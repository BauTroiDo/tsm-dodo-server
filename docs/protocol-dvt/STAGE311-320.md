# Batch Steps 311–320 — FollowNpc active-skill visibility and exclusive weapon boundary

Status: **COMPLETE — owner build gate pending.**

## Step 311 — Battle skill picker authority
DVT `UISkillPick.InitNPCSkill` is the direct UI evidence for which FollowNpc skills are actively selectable in battle.

It adds normal skills, soul skills, learned special skill, upgrade skill and an eligible exclusive-weapon skill.

## Step 312 — Passive is not an active picker skill
Although `RoleController:GetSkillLv` can return `npcData.passiveSkillLv`, `UISkillPick.InitNPCSkill` does not add `passiveSkill`.

Therefore GetSkillLv support alone is not evidence that passiveSkill may be sent as an active C:050 command.

Kotlin intentionally keeps passiveSkill out of `BattleFighter.skills`.

## Step 313 — SkillData CanUse
DVT `SkillData:CanUse()` returns true only when:
- useLimit != 0
- fightWay != 0

The FollowNpc picker explicitly applies CanUse to learned special skills and exclusive-weapon skills.

## Step 314 — Special active visibility
The Steps 301–310 special-skill snapshot now additionally requires the server SkillDef to satisfy the Lua CanUse condition.

A learned but non-battle special skill is not exposed as an active command skill.

## Step 315 — Upgrade active boundary
The picker adds the upgrade skill when upgradeLv > 0. Server additionally requires a valid SkillDef with CanUse semantics before exposing it as an active battle command.

This is defensive command validation consistent with battle-selectable skill semantics; no unknown formula is added.

## Step 316 — Exclusive weapon data format
Lua `ExclusiveWeaponData.New` proves the lookup key is item ID + enhance level and each row carries skillId + skillLv.

`ExclusiveWeapon.GetSkill(id, lv)` returns exactly that row's skill pair.

## Step 317 — Exclusive warrior ownership is also required
Lua does not accept a weapon merely because it has an exclusive skill row.

`ExclusiveWeapon.CheckExclusiveWarrior(itemId, role)` also requires:
- ExclusiveWeapon data for item;
- ItemData for item;
- ItemData.spare3 base NPC;
- membership resolution through `collectWarriorSortDatas` for the actual FollowNpc npcId.

## Step 318 — Kotlin exclusive boundary
`ThingData.enhanceLevel` is available, but the inspected Kotlin data layer has no ExclusiveWeapon_C loader/model and no equivalent collectWarriorSort ownership table/resolver.

Therefore implementing exclusive skills from item ID + enhanceLevel alone would be incomplete and could grant another warrior's exclusive skill.

No speculative exclusive skill snapshot was added.

## Step 319 — Soul boundary
UISkillPick confirms equipped soul skills are actively selectable, and GetSkillLv can resolve their levels.

Current server FollowNpcData has soulId but the inspected Kotlin battle path has no authoritative equipped-soul skill table equivalent to Lua `Soul.GetEquippedSoul`.

No soul skill IDs/levels are fabricated.

## Step 320 — Closure
FollowNpc active battle snapshot now distinguishes lookup-only passive semantics from actually selectable skills, and special/upgrade visibility is constrained by loaded SkillDef battle usability.

Exclusive weapon and soul remain explicit missing-data boundaries rather than guessed implementations.
