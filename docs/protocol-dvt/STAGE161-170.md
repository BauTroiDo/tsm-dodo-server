# Batch Steps 161–170 — Status lifecycle and restore contract

Status: **COMPLETE — owner build gate pending.**

## Step 161 — Round transition evidence
`FightField.SetCountDown` increments `fightRound` when the next command phase starts. `FightManager.RevAttackSkill` marks the received S:050-001 action batch as the active round. The client does not locally derive status duration from animation classes.

## Step 162 — Restore packet contract
`protocal.lua` defines S:053-001 <戰鬥狀態回復> as repeated:
- col Byte
- row Byte
- status kind Byte
- skill ID UInt16

`FightManager.RevRestoreStatus` reads exactly that shape and calls `fightRole:HandleStatus(status_kind, skillId)`.

## Step 163 — Restore identity is group + source skill
The restore packet does not send a replacement duration or generic status enum. Client behavior is driven by the status group and source skill ID. Kotlin `StatusRestore(col,row,statusKind,skillId)` and `serializeStatusRestores` already match this Lua wire shape.

## Step 164 — Independent status groups
Lua maintains separate `status_Kind` entries for Seal, Vary, Faint, Spec and Strong. Therefore expiry of one modeled group must not clear unrelated groups.

Kotlin grouped status storage already provides this isolation; expiry removes only the expired group.

## Step 165 — First-round duration boundary
A status inflicted during the current action phase must not lose a duration count before that action phase has completed. Kotlin records `appliedRound` and skips decrement while `appliedRound >= currentRound`.

No new duration formula is introduced here; this preserves the existing client-facing round boundary while avoiding immediate expiry of round=1 effects.

## Step 166 — Existing status consumes one completed round
Statuses present before the current action phase decrement after actions. A status reaching zero generates one S:053-001 restore entry and is then removed from its own group.

## Step 167 — Restore ordering
`BattleManager.broadcastRoundResult` sends:
1. S:050-001 action results;
2. fly-out when present;
3. S:053-001 status restores.

This is compatible with the client contract: status application/ordinary attr effects are consumed from S:050-001 first, then restore invokes `HandleStatus` separately.

## Step 168 — Death/revive evidence boundary
`FightManager.RevChangeAttrib` revives presentation when HP changes from <=0 to >0, but the inspected Lua does not prove a universal rule that death must clear all modeled status groups.

Therefore this batch does **not** invent a death-clears-status policy. Kotlin also skips duration decrement for non-alive fighters; runtime behavior beyond the proven packet contract remains an explicit follow-up boundary.

## Step 169 — Lifecycle regression coverage
Added `DvtBattleStatusLifecycleTest` covering:
- newly applied round=1 status is not consumed immediately;
- it restores on the following completed round;
- restore preserves status group and source skill ID;
- multiple groups expire independently.

## Step 170 — Batch closure
No production lifecycle rewrite was necessary after the Lua re-audit. Current Kotlin group storage and S:053-001 serializer match the proven client contract for modeled group expiry.

The important unresolved boundary is status behavior while dead and after revive; Lua evidence inspected here is insufficient to impose a new server rule.
