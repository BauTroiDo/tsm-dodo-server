# Batch Steps 201–210 — Heal/revive packet and formula boundaries

Status: **COMPLETE — owner build gate pending.**

## Step 201 — S:050-001 HP wire contract
`FightManager.RevAttackSkill` / `AttackData.New` read each target attribute as:
- Attr_Kind Byte
- Value UInt32
- Sign Byte

The Lua comment states Sign 0 = positive, 1 = negative.

## Step 202 — Kotlin sign serialization
`BattleManager.serializeSkillResults` writes:
- attr kind;
- 32-bit value;
- `isPositive ? 0 : 1`.

This matches the DVT S:050-001 client contract for healing and damage sign.

## Step 203 — Client applies positive HP through normal effect path
`FightRoleController.RunEffect` sends non-status attributes to `SetAttrEffect(attrKind, sign, value)`.

Healing therefore needs an HP attribute with sign 0. No separate S:050 heal packet is required by the inspected Lua path.

## Step 204 — Revive presentation boundary
The previously audited client attribute path clears dead presentation when HP changes from <=0 to >0. fightWay 8 selects dead friendlies; positive HP is the client-visible revive transition.

No special revive damage/heal formula is inferred.

## Step 205 — MaxHP cap
Kotlin computes actual heal against `target.maxHp - target.hp` and applies `coerceAtMost(maxHp)`.

Only the effective positive delta is serialized. This prevents server/client HP divergence from overheal.

## Step 206 — Zero-effective heal
At full HP the current resolver emits no HP attr because the effective delta is zero.

The inspected Lua proves how a received delta is applied but does not require an explicit HP +0 entry. No fake zero-delta packet is introduced.

## Step 207 — Multi-target area source
Lua `SkillData:GetFightArea(skillLv)` is authoritative for level-growing areas:
- grow type 1: 1 -> 2 -> 5 -> 6 -> 8 by level bands;
- grow type 2: 3 -> 5 -> 6 -> 8.

Kotlin `getFightArea` already mirrors these exact bands.

## Step 208 — Heal/revive uses normal area geometry
The resolver applies the computed fightArea before effect calculation, so friendly heal/revive uses the same Lua-audited target geometry from Steps 181–190.

For fightWay 8, eligibility is additionally dead-target-only; ordinary heal remains alive-target-only.

## Step 209 — Area 255 revive correction
A remaining mismatch existed in `resolveTargets(255)`: it returned `getAll()` directly and bypassed the dead-target eligibility predicate.

It now filters all-field occupants through the same eligibility rule. Thus an all-field revive cannot apply healing to living occupants merely because area 255 includes both parties.

Added regression coverage with dead/live occupants on both sides.

## Step 210 — Formula boundary and closure
The current `calculateHeal` formula is server policy and is **not** declared Lua-proven by this batch. Lua/data inspected here proves packet shape, sign, area growth, target eligibility and HP application semantics, but not the numeric healing equation.

No speculative formula replacement was made.
