# Batch Steps 91–100 — Command control and mixed dispel semantics

## Step 91 — Client control evidence
FightField.IsCanControl explicitly returns false when Faint status is Chaos or Taunt, and also while any Seal status is active.

## Step 92 — Chaos command block
BattleFighter now distinguishes isStunned from isCommandBlocked. Chaos blocks player command input without falsely classifying it as a Seal stun.

## Step 93 — Player action validation
setPlayerAction rejects actions while isCommandBlocked, matching client control availability.

## Step 94 — Ready-state parity
allPlayersReady excludes command-blocked controlled fighters, so a Chaos player cannot deadlock the round waiting for an input the client will not send.

## Step 95 — NPC Chaos boundary
No Chaos target-redirection behavior is invented for NPC AI. Current client evidence proves player command blocking, not authoritative server redirect rules.

## Step 96 — Mixed dispel audit
The Step61–70 implementation short-circuited every skill present in a clear list. That could erase attack/heal behavior for mixed-effect skills.

## Step 97 — Clear independent of primary effect
Group clearing now happens independently before the primary skill calculation.

## Step 98 — Pure friendly dispel
A clear-list skill only short-circuits ordinary damage calculation when its fightWay is one of the client-proven friendly utility ways 6,7,8,14.

## Step 99 — Offensive mixed clear
A skill that clears a group but is not friendly utility continues through attack calculation after applying its clear effect.

## Step 100 — Build gate
Run ./gradlew test build. Poison tick and Chaos redirect remain deliberately unimplemented until authoritative server/result evidence is found.
