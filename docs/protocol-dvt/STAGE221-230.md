# Batch Steps 221–230 — Command submission and resource timing

Status: **COMPLETE — owner build gate pending.**

## Step 221 — C:050 server packet shape
`BattleCommandHandler` consumes the DVT battle-command payload as:
- srcCol Byte
- srcRow Byte
- targetCol Byte
- targetRow Byte
- skill/item ID UInt16 LE
- two trailing check bytes

Skill is sub 1; item is sub 2. The handler requires the 8-byte payload before parsing.

## Step 222 — Authoritative source identity
The server locates the actor by the C:050 source coordinates, then verifies either actor roleId or masterId belongs to the sending player. This is required for player-controlled follow NPC commands.

## Step 223 — Client command-control evidence
Lua `FightField.IsCanControl` refuses control when the current fighter:
- has HP 0;
- is Chaos/Taunt;
- is in Seal status.

Kotlin queue gating uses alive + command-blocked state and the execution path rechecks blocking before the AGI turn.

## Step 224 — ACK boundary
`BattleCommandHandler` emits S:053-005 ActSetOK only when `handlePlayerAction` returns accepted.

The client-side battle flow uses the accepted-action transition to advance control. An accepted command must therefore remain stable until execution.

## Step 225 — Proven replay/overwrite risk
Before this batch, `setPlayerAction` unconditionally assigned `fighter.pendingAction = action` after validation.

A duplicate/replayed C:050 for the same fighter could replace an already accepted command before round resolution, despite the earlier command already having received S:053-005.

## Step 226 — One accepted command per fighter per round
`setPlayerAction` now rejects a command when `fighter.hasActed` is already true or `pendingAction` is non-null.

The first authoritative accepted command remains immutable for that round; duplicate/replayed commands receive no new ACK.

## Step 227 — SP deducted at execution, not queue
Queue validation checks that current SP can satisfy the configured requirement, but does not mutate SP.

`BattleSkillResolver.resolveSkill` performs the actual SP deduction after target resolution. Thus a command accepted into the queue does not immediately burn resource.

## Step 228 — SP exactly once
Because duplicate commands can no longer replace/requeue an accepted fighter action and the action is resolved once in `resolveRound`, the resolver's SP mutation is tied to one execution path.

No extra SP mutation was added to the network handler or queue layer.

## Step 229 — Dead/blocked after queue
`resolveRound` snapshots alive queued actors, then immediately rechecks `fighter.isAlive` before each AGI turn and rechecks `isActionBlocked`.

If a faster actor kills or applies a client-proven blocking state before this fighter's turn, its queued action is not executed; therefore the skill resolver does not consume its SP.

## Step 230 — Regression coverage and boundary
Added `DvtBattleCommandSemanticsTest`:
- first accepted command cannot be replaced by a duplicate;
- a dead actor cannot queue a command.

This batch does not invent command-edit/cancel semantics. The DVT evidence used here supports accepted-command stability and client control blocking, not an arbitrary server-side action replacement feature.
