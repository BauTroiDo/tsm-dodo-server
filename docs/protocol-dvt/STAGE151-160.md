# Batch Steps 151–160 — Enemy status-only vs damage+status execution

Status: **IN PROGRESS — build/test gate pending owner pull.**

## Step 151 — Lua wire contract re-audit
Re-read `SkillData.lua`, `protocal.lua`, `FightManager.RevAttackSkill` and `FightRoleController.RunEffect`.

Client evidence:
- `SkillData.attribute` is the skill's attribute kind.
- S:050-001 carries repeated `Attr_Kind + Value + Sign` entries per target.
- `RunEffect` recognizes `EAttribute.Seal/Vary/Faint/Spec/Strong` and calls `HandleStatus(statusKind, skillID)`.
- Therefore applying a modeled status only in Kotlin memory is insufficient: successful status application must also be represented in the S:050-001 attribute list.

## Step 152 — Enemy status-only classification
Do not classify by target side or by guessed skill names.

For modeled skills, an enemy skill is treated as status-only only when all are true:
- target is not friendly-only;
- `SkillData.attribute` is one of Seal/Vary/Faint/Spec/Strong;
- `round > 0`;
- `statusFromSkillId(skillId)` has a client-proven concrete modeled status.

This follows the Lua data field instead of forcing every enemy skill through damage calculation.

## Step 153 — No fake HP damage
Added `BattleDamageCalc.calculateStatusOnly`.

It preserves the server's existing hit/status chance policy but does not calculate or emit HP damage. The existing chance formula is **not claimed as newly proven by Lua**; it is retained rather than inventing a replacement formula.

Damage+status skills whose `SkillData.attribute` is not itself a status attribute remain on the existing damage path.

## Step 154 — Status Attr_Kind wire propagation
`BattleSkillResolver` now adds the corresponding status group attribute to `TargetResult.attrChanges` when a modeled status is successfully applied:
- group 1 → `EAttribute.SEAL`
- group 2 → `EAttribute.VARY`
- group 3 → `EAttribute.FAINT`
- group 4 → `EAttribute.SPEC`
- group 5 → `EAttribute.STRONG`

The same wire fix is applied to the friendly utility path from Steps 141–150. Value/sign are not used by Lua for status attributes; the client dispatches by `Attr_Kind` and resolves the concrete identity from `skillID`.

## Step 155 — Regression tests
Added `DvtBattleStatusExecutionTest`:
- enemy Chaos/status-attribute execution must never mutate HP or serialize HP delta;
- when the existing chance policy applies Chaos, Faint Attr_Kind must be present;
- friendly SameHeart must expose Vary Attr_Kind, preserve HP, and set grouped status.

## Evidence boundary
Lua proves the packet shape, status-group Attr_Kind dispatch, concrete status identity mapping, and that `SkillData.attribute` is the declared attribute kind.

Lua inspected in this batch does **not** prove a replacement server hit/status probability formula. No new formula was invented.
