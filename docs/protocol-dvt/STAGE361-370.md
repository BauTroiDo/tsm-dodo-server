# Batch Steps 361–370 — ffWar_Style transport and catch reference

Status: **COMPLETE — owner build gate pending.**

## Step 361 — Exact ffWar_Style packet
DVT protocal.lua maps S:011-010 to FightManager.FightFieldWarStyle.

Payload:
- battle style Byte
- round UInt16
- optional limit Byte
- fightMark UInt32

FightFieldWarStyle stores the first byte directly into FightField.ffWar_Style.

## Step 362 — Style is independent server state
This proves ffWar_Style is delivered by the server. It is not derived client-side from EWar.

Therefore EWar and EFFWar_Style must remain distinct server concepts.

## Step 363 — Kotlin already sends S:011-010
BattleManager.sendBattleInit already calls responseSender.sendBattleFieldType after S:011-250.

Before this batch it always sent EWarStyle.NORMAL.

## Step 364 — Proven Kotlin state-loss gap
Hard-coding NORMAL discards any future LifePK, WorldBoss, NewChaos and other battle-field style semantics before the client receives them.

This also prevents authoritative command checks from consulting the same style state sent to Lua.

## Step 365 — Production fix
BattleInstance now owns a separate warStyle field, defaulting to EWarStyle.NORMAL.

The default deliberately preserves current behavior and does not invent EWar→EFFWar_Style mappings.

## Step 366 — Packet fix
BattleManager.sendBattleInit now sends battle.warStyle in S:011-010 instead of hard-coded NORMAL.

Each battle creator can set a non-normal style only when its source semantics are proven.

## Step 367 — Escape boundary
DVT DoClick rejects escape for ffWar_Style LifePK=11 and WorldBoss=16.

No production escape gate is added yet because current battle creators do not yet provide authoritative non-normal warStyle values.

## Step 368 — PC original catch evidence
Reference repository bboycs/tsonline-server-tl BattleAbstract.CatchPet checks:
- player has pet capacity;
- player level + 5 >= target level;
- NPC notPet == 0;
- success rate = (1 - currentHp/maxHp) * 100.

On success it adds the NPC as a pet and marks the target outBattle.

## Step 369 — Evidence priority for catch formula
The PC formula is strong secondary evidence and independently agrees with DVT's +5-level rule.

However DVT Lua is client-side and does not expose the authoritative random success formula. The PC formula therefore remains secondary evidence, not a DVT-proven formula.

The current Kotlin 30–95% HP+level formula is likewise not DVT-proven.

No probability replacement is made in this batch until result/effect behavior and version compatibility are audited further.

## Step 370 — Closure
The server now preserves the exact protocol concept needed for DVT ffWar_Style without guessing mappings. Catch formula evidence has been strengthened but intentionally not promoted above DVT evidence.
