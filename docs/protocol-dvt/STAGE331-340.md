# Batch Steps 331–340 — Defend/catch/escape command path audit

Status: **COMPLETE — owner build gate pending.**

## Step 331 — UI command IDs
DVT UIFight maps:
- defense -> SetConSkill(17001), then DoClick
- catch -> SetConSkill(15002), target selection follows
- escape -> SetConSkill(18001), then DoClick

These are carried through the skill command path, not separate C:050 packet formats.

## Step 332 — Guest escape
Guest/spectator escape is separate: UIFight sends C:011-001 and returns.

It must not be conflated with normal battle escape 18001.

## Step 333 — Escape war-style client gate
UIFight blocks normal escape in LifePK and WorldBoss before SetConSkill.

This is client UI evidence; authoritative server war-style enforcement requires matching constants/semantics before patching.

## Step 334 — Catch UI gates
UIFight permits the catch button only for the player-controlled Player actor and refuses when the follow-NPC roster is already full.

These are pre-selection UI gates in addition to any skill/target behavior.

## Step 335 — Shared CaseSkill path
SetConSkill invokes CaseSkill semantics. CaseSkill starts from hand attack and accepts a requested skill only after its common checks: SkillData existence, Except fightWay gate, SP, source role, GetSkillLv > 0, summon equipment and player bow equipment where applicable.

## Step 336 — Kotlin classification
BattleCommandHandler receives all three through C:050-001 and classifies IDs into KIND_DEFEND/KIND_ESCAPE/KIND_CATCH.

That is a server-internal representation; it does not imply separate wire opcodes.

## Step 337 — Important validation boundary
Because the three IDs become non-KIND_SKILL internally, current setPlayerAction does not run its normal skill target/SP/learned checks for them.

However, the inspected repository contains no textual SkillData rows or learned-skill initialization proving how 15002/17001/18001 satisfy DVT GetSkillLv in runtime data.

Patching them through the normal learned-skill set without that data could incorrectly disable built-in commands.

## Step 338 — No speculative restriction
This batch does not blindly require these command IDs to appear in BattleFighter.skills.

Their Lua UI/CaseSkill path is proven, but their built-in/learned ownership source is not yet proven from the available source-only snapshot.

## Step 339 — Item path
C:050-002 remains a distinct item command. Kotlin validates target, owner session and item availability/effect through BattleItemResolver before ACK.

No mismatch is asserted here without auditing the exact Lua fight-item picker/use restrictions and item effect semantics.

## Step 340 — Closure
The wire/path distinction for defend/catch/escape is now explicit and the Kotlin bypass boundary is documented. No production patch is made until the SkillData/Role initialization evidence for IDs 15002/17001/18001 is available.

## Build gate
Documentation only; no production code changed in Steps 331–340.
