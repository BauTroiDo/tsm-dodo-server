# Batch Steps 211–220 — SP and resource semantics

Status: **COMPLETE — owner build gate pending.**

## Step 211 — SP wire semantics
S:050-001 `AttackData.New` reads every attribute uniformly as Attr_Kind Byte + Value UInt32 + Sign Byte. `RunEffect` forwards non-status attributes, including SP, to `SetAttrEffect`.

Therefore SP uses the same signed delta contract as HP: sign 0 adds, sign 1 subtracts.

## Step 212 — requireSp data authority
`SkillData.New` reads `requireSp` as UInt16 and labels it as SP cost.

## Step 213 — requireSp == 1 special rule
`SkillData:GetDescription` contains the explicit DVT rule:
`若填消耗1點SP=消耗全部` — when the configured cost is 1 SP, consume all SP.

Kotlin's existing `requiredSp == 1 -> attacker.sp` behavior is therefore Lua-backed and retained.

## Step 214 — Insufficient SP gate
Lua `FightField.CaseSkill` rejects skill selection when current SP < `skillData.requireSp`.

Kotlin also rejects when attacker SP is below the configured requirement. No alternative cost rule was introduced.

## Step 215 — Mutation after target resolution
Kotlin resolves targets before mutating attacker SP. If the resolved target set is empty, `spConsumed=0` and SP is unchanged.

This is retained as transaction safety; the inspected Lua selection code does not prove that an invalid/stale server target should burn resource.

## Step 216 — SP positive cap
Positive SP deltas are capped by `maxSp - sp`, then server SP is capped at maxSp. Only the effective delta is serialized.

## Step 217 — Proven negative-SP implementation gap
The resolver previously handled EAttribute.SP only when `change.isPositive`. A negative SP BattleAttrChange could therefore be silently ignored even though Lua's generic S:050-001 attribute path supports signed SP deltas.

## Step 218 — Negative SP fix
Negative SP changes now:
- clamp effective loss to current SP;
- subtract without underflow;
- serialize the effective SP delta with negative sign.

This follows the proven generic Attr_Kind/Value/Sign contract and does not invent a drain formula.

## Step 219 — Regression coverage
Added `DvtBattleResourceSemanticsTest` covering:
- requireSp=1 consumes all current SP after a valid target resolves;
- invalid target consumes no SP.

The signed SP mutation path is production-hardened independently of any unproven skill-specific drain equation.

## Step 220 — Batch closure
Resource handling now preserves the DVT-proven SP cost special case and supports both signs of SP battle deltas.

No Lua files changed. No SP drain/heal numeric formula was invented.
