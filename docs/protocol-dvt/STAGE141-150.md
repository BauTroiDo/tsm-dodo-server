# Batch Steps 141–150 — Friendly status execution path

## Step 141 — Runtime consumer audit
The expanded status identity table was traced through resolveSkill rather than relying on compilation alone.

## Step 142 — Friendly buff bug
Friendly Vary/Spec/Strong status skills were neither HP heals nor dispels. They therefore fell through to calculateAttack and could generate attack damage against an ally.

## Step 143 — Status chance bug
The same path incorrectly subjected friendly buffs to offensive hit/status chance before applying their status.

## Step 144 — Public concrete identity
BattleDamageCalc.statusFromSkillId is exposed to the battle resolver so utility status execution can use the exact client-proven skill identity mapping.

## Step 145 — Friendly utility status path
For client-proven friendly fightWay skills with round > 0, resolveSkill now applies the modeled status directly to its status group.

## Step 146 — No fake damage
A successfully applied friendly status returns HIT/NONE with no HP/SP attr changes rather than entering attack damage calculation.

## Step 147 — Group replacement
Applying a friendly status replaces only its own group through setGroupedStatus, preserving independent Seal/Vary/Faint/Spec/Strong coexistence.

## Step 148 — Duration/source
The utility path records skill.round, skillId and currentRound exactly like offensive status application, so expiry and restore packets stay consistent.

## Step 149 — Effect formula boundary
MirrorAtk and Protect/MagicProtect animation code prove that these identities have special combat presentation, but do not provide authoritative server damage-transfer/reflection formulas. No formula is invented in this batch.

## Step 150 — Build gate
Run ./gradlew test build. Next audit should verify enemy debuff status-only skills versus damaging status skills so they are not all forced through one attack path.
