# Batch Steps 541–560 — Sequential battle action playback

Status: **PRODUCTION PATCHED — build/runtime gate pending.**

## Runtime evidence
After the RoleAppear alignment fix, the owner confirmed the enemy renders. Combat then exposed a second defect: player and NPC attacks begin at essentially the same time with no action spacing.

## DVT client evidence
FightManager.RevAttackSkill:
- receives S:050-001;
- calls FightField.ClearAllAttack();
- parses every embedded action immediately;
- calls AddEffect + FightField.AttackSkill for each parsed action.

FightField.UpdateAttack then advances each active Attack state machine every client frame. There is no client-to-server animation-complete ACK.

Therefore embedding several independent AGI commands in one S:050-001 starts their attack state machines in the same receive frame.

SkillData.New exposes spendSecond as the DVT skill timing field.

## Secondary original-server evidence
PC BattleAbstract.execute processes the ordered command registry sequentially.
execCommand broadcasts one S:050-001 command, then sleeps for the skill's configured delay before executing the next command. Items use their own playback delay.

This is secondary evidence only; DVT Lua remains authoritative.

## Kotlin mismatch
BattleInstance.resolveRound correctly establishes ordered ActionResults, but BattleManager.broadcastRoundResult previously serialized the complete ActionResult list into one S:050-001. That packet shape made all independent actors animate concurrently.

## Patch
BattleManager now:
1. keeps the already-resolved authoritative AGI order;
2. serializes one ActionResult per S:050-001;
3. broadcasts it;
4. waits the DVT SkillData.spendSecond playback duration before broadcasting the next action;
5. uses a 1000 ms minimum only when the command has no usable SkillData timing (notably basic/special commands);
6. retains ROUND_END_DELAY_MS after the final action.

This does not change damage, target selection, AGI ordering, statuses or AI decisions.

## Runtime gate
Run ./gradlew test build.
Then test a simple one-player vs one-NPC battle and verify:
- only one actor begins an attack at a time;
- the second action waits for the first action;
- animations are not cut off by the next S:050-001;
- next-round countdown/control resumes normally.

If a specific skill is cut short or leaves an excessive pause, record its skill ID. The next audit should compare that skill's spendSecond with its concrete Lua Attack state machine rather than applying a global arbitrary delay.
