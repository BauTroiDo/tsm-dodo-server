# Batch Steps 321–330 — Exclusive weapon data availability boundary

Status: **COMPLETE — owner build gate pending.**

## Step 321 — Exact client data files
DVT DataManager loads:
- `Data/IOS_CollectWarriorSort_C.dat`
- `Data/IOS_ExclusiveWeapon_C.dat`

These are the authoritative client tables used by ExclusiveWeapon ownership/skill resolution.

## Step 322 — CollectWarriorSort format
`CollectWarriorSortData.New` reads:
- index UInt16
- three NPC IDs UInt16
- nft Byte

The table groups the base NPC ID with equivalent/transformed NPC IDs for exclusive-weapon ownership.

## Step 323 — ExclusiveWeapon format
`ExclusiveWeaponData.New` reads key itemId UInt16 + enhanceLv Byte, then skillId UInt16 + skillLv Byte, two attribute pairs, element data and plus attribute.

`ExclusiveWeapon.GetSkill(itemId, enhanceLv)` uses the exact keyed row.

## Step 324 — Item-side ownership key
Kotlin `ItemDef` already preserves `spare3`, matching Lua's `itemDatas[itemId].spare3` base-NPC key.

## Step 325 — Runtime item enhance level
Kotlin `ThingData.enhanceLevel` already preserves the exclusive weapon enhancement level used by Lua.

## Step 326 — Missing server data files
The repository tree does not contain either authoritative DAT file under the names loaded by DVT:
- IOS_ExclusiveWeapon_C.dat
- IOS_CollectWarriorSort_C.dat

The current GameDataManager also has no models/loaders for them.

## Step 327 — Why no speculative loader wiring
Although both binary formats are now proven, a loader with no authoritative runtime files would not produce battle parity.

More importantly, skipping CollectWarriorSort ownership would permit a FollowNpc to receive another warrior's exclusive skill.

No fake fallback table is introduced.

## Step 328 — Normal NPC skill picker nuance
`UISkillPick.InitNPCSkill` adds the three normal NPC skill IDs without applying `SkillData:CanUse()`.

Therefore the server must not globally impose CanUse on all normal pet skills merely because special/exclusive paths use it.

The existing per-pet learned-level rule remains unchanged.

## Step 329 — CaseSkill remains execution-selection authority
Regardless of picker visibility, `FightField.CaseSkill` still enforces:
- skill exists;
- fightWay Except gate;
- SP;
- role exists;
- GetSkillLv > 0;
- summon equipment;
- player bow equipment.

Existing Kotlin command gates mirror these proven restrictions without inventing a global normal-skill CanUse rejection.

## Step 330 — Closure
Exclusive weapon support is data-blocked, not format-blocked. The exact missing files and formats are documented so the server can add it when those client DAT resources are supplied.

No production patch was required in this batch beyond the already-green 311–320 active-skill behavior; this batch deliberately avoids an unsafe partial implementation.

## Build gate
