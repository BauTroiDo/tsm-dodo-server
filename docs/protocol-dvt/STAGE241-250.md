# Batch Steps 241–250 — Round command lifecycle

Status: **COMPLETE — owner build gate pending.**

## Step 241 — Lua round reset
DVT `FightField.SetCountDown` advances the fight round and resets per-fighter command-selection flags, including `blnChoose` and `blnActSetOK`.

The next command phase is therefore a fresh submission phase.

## Step 242 — Kotlin round reset
At the end of `BattleInstance.resolveRound`, Kotlin clears every fighter's:
- `pendingAction`;
- `hasActed`;
- `comboMultiplier`.

This resets the duplicate-command guard introduced in Steps 221–230 for the next round.

## Step 243 — Normal executed action cleanup
After an action executes, its fighter has `pendingAction=null` and `hasActed=false`. The end-of-round sweep repeats the cleanup defensively.

## Step 244 — Defend cleanup
Defend commands are processed before AGI actions. The fighter is marked defending and its command state is immediately cleared.

The end-of-round sweep still guarantees a clean next command phase.

## Step 245 — Blocked-after-queue cleanup
A fighter can queue while controllable and then receive a Seal/Chaos/Taunt-class blocking state from a faster actor.

At its AGI turn Kotlin rechecks `isActionBlocked`, clears the queued command and does not call the skill resolver. Thus no execution-time SP is consumed.

## Step 246 — Dead-before-turn cleanup
A fighter killed before its AGI turn is skipped by the action loop. Its queued command is not executed and is cleared by the unconditional end-of-round sweep.

No stale command survives into the next round.

## Step 247 — Item/escape/catch cleanup
These action kinds share the same post-action command cleanup and final round sweep. Their command lock does not persist into a later round.

## Step 248 — Duplicate guard reset boundary
The one-command-per-round guard checks `hasActed || pendingAction != null`.

Because both fields are reset at round completion, it rejects replay only inside the current command phase and does not permanently lock the fighter.

## Step 249 — Regression coverage
Extended `DvtBattleCommandSemanticsTest`:
- accepted command executes, round ends, state clears, and next-round submission is accepted;
- queued actor that becomes blocked does not execute, command state clears, and can submit again after status removal.

Existing duplicate, dead actor and revive-target tests remain.

## Step 250 — Batch closure
No production lifecycle rewrite was necessary in this batch. Existing Kotlin round cleanup is compatible with the inspected DVT fresh-round reset behavior and is now protected by regression tests.

No Lua changed. No action formula changed.
