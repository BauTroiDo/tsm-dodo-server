# Batch Steps 371–380 — Catch result and ownership

Status: **COMPLETE — owner build gate pending.**

## Step 371 — DVT S:050-001 result path
DVT RevAttackSkill parses catch like every other battle skill result:
segment length, source position, skillId, fightArea, target count, then AttackData target/result/action/attributes.

There is no separate client-side “catch success packet” in this path.

## Step 372 — Client presentation boundary
RevAttackSkill passes the server-provided skillId and AttackData into FightRole effects.

Therefore the server remains authoritative for the result represented by the skill/effect; Lua does not compute catch probability in RevAttackSkill.

## Step 373 — Current Kotlin catch representation
Kotlin currently emits CATCH_NET_SUCCESS=15003 on success and CATCH_NET_FAIL=15002 on failure, with HIT/MISS and no attribute change.

This remains to be validated against DVT SkillData/effect animation data before changing IDs.

## Step 374 — Capture persistence exists
Earlier inspection concern is corrected: capturedNpcs is consumed by BattleManager.handleBattleEnd.

On a winning battle, PetSystem.addFollowNpc creates the pet in the follow cache and response packets update the client. PetSystem marks its cache dirty for repository persistence.

## Step 375 — Proven multiplayer ownership bug
Before this batch capturedNpcs stored only npcId.

handleBattleEnd loops every player session and then loops the same capturedNpcs list, so a capture in a multi-player/join battle could award the captured NPC independently to every participating player.

This is server-authority corruption unrelated to probability and must be fixed.

## Step 376 — Production ownership fix
BattleInstance now records each capture as:
capturer playerId -> npcId.

The ownerPlayerId already comes from the action's fighter ownership, so no inference is required.

## Step 377 — Award fix
BattleManager.handleBattleEnd now processes a captured NPC only when capturerPlayerId equals the current playerId.

A capture can no longer fan out to unrelated participants.

## Step 378 — PC original formula
bboycs/tsonline-server-tl BattleAbstract.CatchPet remains secondary evidence:
rate = (1 - currentHp/maxHp) * 100,
with +5 level and notPet/capacity checks.

It agrees with DVT +5 but DVT Lua still does not expose the random formula.

## Step 379 — Probability intentionally unchanged
Current Kotlin 30–95% HP+level probability is not DVT-proven. The PC formula is stronger historical server evidence, but replacing probability is deferred until DVT skill/effect data around 15002/15003 and any available mobile-server reference are exhausted.

## Step 380 — Closure
The catch lifecycle is now traced through S:050-001 and end-of-battle pet creation. The concrete multiplayer ownership corruption is fixed without inventing gameplay formulas.
